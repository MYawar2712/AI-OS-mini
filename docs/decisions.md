# Decisions (ADR-lite)

| ADR | Decision | Options considered | Why chosen | Trade-off |
|---|---|---|---|---|
| ADR-001 | **Narrow scope to first-touch triage** (intent, priority, routing, escalation, summary) | Auto-replies; full resolution assistant; KB search bot | Triage touches every ticket, sits upstream of SLA/routing/reporting, and is low blast-radius (internal only) | Smaller visible "wow"; time saving depends on review UX |
| ADR-002 | **LLM proposes, deterministic rules dispose**: rules can only raise priority or add escalations | Pure LLM; pure rules; LLM with rules as hints | Safety-critical decisions (P1, churn, injection, PII) must be auditable and can't be talked out of by ticket text | More code to maintain; rules can over-escalate (watched with escalation precision gate G8) |
| ADR-003 | **Taxonomy in YAML, enums in Pydantic, consistency enforced by tests** | Enums generated at runtime from YAML; YAML only | Literals give a static JSON Schema and IDE help; the test stops drift | Changing a label needs two edits (caught by CI) |
| ADR-004 | **Synthetic data only, labelled everywhere; anchored customers + seeded random fill (seed=42)** | Scrape public forums; ask for real tickets | No access to production data; privacy; reproducibility | Realism unproven (A-17); labels are single-annotator |
| ADR-005 | **Low-cost model tier by default** (model choice detailed in ADR-013) | Larger/pro-tier models | Owner asked for extremely low cost | Possibly lower accuracy on nuanced tickets. Day 4 will compare one run on a larger model to measure the gap |
| ADR-006 | **Mixed-language tickets: classify normally; mixed language alone is not an escalation reason** | Escalate all non-English; translate first | Owner stated traffic is mostly English. Escalating every Roman-Urdu phrase would inflate human-touch | Non-English-dominant tickets aren't handled in v1 (non-goal; fallback to human) |
| ADR-007 | **If no API key is set, the naive LLM baseline records `not_run`**; it is never estimated or simulated | Fake/simulated LLM outputs; skip baseline entirely | Honesty rule: no simulated numbers presented as results | Comparison can be partial; re-run when a key is present |
| ADR-008 | **Case PASS requires every critical field. Over-prioritising by one level is tolerated, any under-prioritisation of P1/P2 is critical** | Exact-match everything; weighted score | Mirrors the real cost asymmetry (missed outage ≫ slightly early attention) | Small over-prioritisation bias isn't penalised. Priority exact-accuracy is reported separately |
| ADR-009 | **Missing-info recall reported but not case-critical in v1** | Make it case-critical | It's useful but not a safety issue. Expected lists are subjective (single annotator) | A system could ignore missing info and still pass cases. Watched in aggregate |
| ADR-010 | **Primary command `python -m scripts.run_day1`; Makefile provided too** | make only | Dev machine is Windows without `make` | Two entry points to keep in sync (Makefile just calls the module) |
| ADR-011 | **Project-local `.venv` + `requirements.txt` (pip)** | uv; poetry | `uv` not installed; pip is universal for evaluators | Slower installs; no lockfile (versions floored, not pinned) |
| ADR-012 | **Labour cost modelled deliberately low (£12–17/h)** | Market-rate loaded cost | Owner request for a demo. A low rate makes the business case conservative | Under-states value; easy to change in `config/settings.yaml` |
| ADR-013 | **LLM provider: Alibaba Cloud Model Studio (International / Singapore), model `qwen3.8-27b` (selected under ADR-016 from `deepseek-v4.1-flash`, `deepseek-v4.1-flash-1017`, `qwen3.8-27b`, `qwen3.8-omni-flash`; `kimi-k3.1-pro` was requested but is not available on the account, and the owner chose to skip Kimi), through its OpenAI-compatible API** (`src/llm_client.py`; provider switchable in `config/settings.yaml`) | Anthropic (kept as an option); Qwen models on the same platform | Owner's account and model choice. The OpenAI-compatible endpoint keeps the client tiny and provider-agnostic | Price per token not yet confirmed. The model spends ~1,000 hidden reasoning tokens per ticket, giving 8 s (DeepSeek) to 28 s (Qwen) median latency on the naive runs. Tickets go to a third-party cloud: fine for synthetic data, but data residency must be reviewed before real tickets |
| ADR-014 | **Scoring revision 2: negation-aware must-not phrases + label-tolerant free-text parser**, re-scored from saved outputs (no new API calls) | Keep substring matching; hand-grade TC10 | Revision 1 failed "Do not approve any refund" as approving a refund, and lost `**Escalate:**`-style sections. Both were harness bugs, not model behaviour | Parser hints were extended *after* seeing the outputs ("untrusted", "system note", "symptom"). This may slightly flatter the naive baseline. Disclosed in rubric §6 |
| ADR-015 | **Archive each model's results before switching models** (`eval/results/archive/<model>/`), plus a side-by-side `model_comparison.md` | Overwrite; per-model filenames everywhere | Keeps the evidence for every model tried, with minimal code change | Manual step for now. Automate per-model result naming on Day 2 |
| ADR-016 | **Model selection by a lexicographic rule fixed before the final run**: critical failures → escalation recall → under-prioritisation → injection → case pass rate → priority accuracy → human-touch → latency (`scripts/compare_models.py`) | Weighted score; pick by eye after seeing results | Safety first and decided in advance, so the choice can't be tuned to the result | Latency only breaks ties: `qwen3.8-27b` won by one case despite 3.5× the latency. Re-evaluate on Day 2 once latency is tuned; `deepseek-v4.1-flash` is the fallback |
| ADR-017 | **LLM extracts facts; deterministic rules set priority, queue and escalation** (`ExtractedFacts` → `src/pipeline/rules.py`). Refines ADR-002: rules no longer only *raise* the model's priority; the model has no priority field at all | LLM sets priority + rules raise only (ADR-002 as written); LLM end-to-end | Day 1: all 4 models read well (92% intent) but over-prioritised (33–50% priority). Facts → rules is auditable (rule IDs in every trace) and unit-testable. Held-out priority accuracy 58% (naive) → 83% (pipeline) | Rules need maintenance when definitions change; a fact the model misreads still flows into the rules (mitigated by independent detectors + human review) |
| ADR-018 | **Pipeline runs the model with reasoning OFF, JSON mode, max 700 tokens** (`config/settings.yaml → pipeline`) | Reasoning on (default) | Fact extraction is simple reading; reasoning off cut median latency from 28 s to ~6.5 s with 12/12 dev and 11/12 held-out | Still above the 5 s gate; harder judgement could suffer (watch via eval) |
| ADR-019 | **v0 storage: append-only JSONL** (`data/runs/audit.jsonl`, `ticketing_outbox.jsonl`, git-ignored) | SQLite; hosted DB | Zero setup, human-readable, replayable into the eval set | No querying/concurrency; revisit on Day 3+ |
| ADR-020 | **v0 interface: CLI triage card + a/e/r review prompt** (`scripts/triage.py`) | Streamlit / Sheets UI now | Proves the full flow including the approval step fastest | Not yet non-developer friendly; Day 5 review screen |
| ADR-021 | **Held-out test set** (`eval/test_cases_holdout.jsonl`, 12 cases written before pipeline code). Tuning uses dev failures only; held-out runs are logged checkpoints | Single 24-case set; no split | Makes the reported score credible (dev was visible while writing prompt/rules) | Small n; each held-out run "spends" some independence, so the checkpoint log records every run |
| ADR-022 | **Taxonomy wording: P2 billing = duplicate or unauthorised payment taken; seat-count/invoice queries stay P3** | Keep "incorrect/duplicate charge" | The old wording made the Day 1 label for TC01 (seat-count query, P3) contradict the P2 definition | None: labels unchanged, definition now matches them |
| ADR-023 | **Review UI in Streamlit** (`app/review.py`), built ahead of Day 3 at the owner's request; calls the same `triage()` and `handoff.record()` as the CLI | FastAPI + HTML/React | Same language as the rest of the system, one command to start, testable with Streamlit AppTest, ~2–3 h instead of ~1–1.5 days | Less control over look and feel; single-user local app (fine for v1 pilot; multi-user hosting is out of scope) |
